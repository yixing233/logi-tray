# 原生版 mouse-tray（C++ / Win32 / D3D11）

Python 版的**全量原生重写**。功能对齐，行为逐模块与 Python 版对照验证。

## 为什么换栈

Python 版的材质渲染全是 CPU 上的 numpy 逐像素运算，而机器上有块 RTX 5060
基本闲置（占用 7%）。同一套液态玻璃算法实测对比：

| 环节 | Python/numpy (CPU) | 原生 D3D11 (GPU) |
|---|---|---|
| 液态玻璃渲染 | 11.12 ms | **0.029 ms** |
| 端到端单帧（含 4.7ms 抓屏） | 16.7 ms | 4.7 ms |

渲染快约 **400 倍**；进程内存 **79.4 MB → 17.8 MB**；
可执行文件 **301 KB**（静态单文件，含 GPU 渲染、HID 协议、托盘、两个窗口，
无运行时依赖）。

## 材质实现：为什么亚克力"看起来假"

这一轮把三个独立的问题查清了，结论都来自实测而非推测。

### 1. 浮窗没有实时模糊 —— 它在抓自己

```
GetWindowDisplayAffinity(浮窗) == 0x00 (WDA_NONE)
```

`Update()` 用 `BitBlt` 在**自己的矩形上**抓屏，而浮窗没有对抓屏隐形，
于是抓到的就是上一帧的自己 —— 每帧把旧画面重新糊一遍，看起来是一块
不会变色的灰板。

自然的修法是设 `WDA_EXCLUDEFROMCAPTURE`，但 **A/B 实测证明此路不通**
（同一二进制，仅一个环境变量不同）：

| | 结果 |
|---|---|
| 不排除 (`WDA_NONE`) | 浮窗正常渲染 |
| 排除 (`0x11`) | **浮窗完全不再被合成，屏幕上看不见** |

本系统上 `WS_EX_LAYERED` 与 `WDA_EXCLUDEFROMCAPTURE` 不能共存。于是分层
窗口方案两难：不排除 → 材质是自我回灌；排除 → 窗口消失。

**结论：要真正的实时模糊，必须放弃「分层窗口 + BitBlt」，改走
DirectComposition（非分层、无需 CPU 抓屏）。** 代码里保留了
`MOUSETRAY_FORCE_EXCLUDE=1` 用于复现该现象，默认关闭。

### 2. 浅色桌面下面板发灰 —— 亮度层的基准错了

用用户截图实测：

| | 亮度 |
|---|---|
| 桌面背景 | 247.6 |
| 面板材质区 | **205.4**（暗 20%）|

根因是亚克力亮度层（对比压缩）写成固定绕 0.5：

```hlsl
lumOut = (lum - 0.5) * 0.5 + 0.5      // 纯白 0.96 -> 0.73
```

任何比中灰亮的背景都会被拉暗。正确做法是绕**背景自身的平均亮度**：

```hlsl
lumOut = (lum - LUM_PIVOT) * LUM_CONTRAST + LUM_PIVOT
```

`LUM_PIVOT` 由 CPU 在缩放眼背景时顺便算出（无需额外 pass）。
修后白底 245 → 面板 **244**（原来 205），深色底仍保留结构。

同一修正也补进了 `glass_effects.py` 的 `_render_acrylic` —— 之前 Python
参考实现**完全没有亮度层**（正是"白贴纸"的成因），导致 GPU/Python 对拍
的亚克力粗粒度差达 42.53；补齐后降到 **5.70**。

### 3. 「实时材质」开关是装饰品

`app.cpp` 里设置了 `opt.realtime` / `opt.fps`，但**没有任何代码读取它们**，
主循环每 30ms 无条件 `Update()`。用 CPU 时间直接测出差别：

| 实时材质 | 浮窗 CPU |
|---|---|
| 开 | 9.37% |
| 关 | **0.00%** |

修法：`Update()` 按开关与 fps 节流；关闭时只在内容指纹变化（电量等）时重绘。

### 4. 阴影过重 + 圆角偏小

用户反馈"圆角问题加上阴影太重"。实测确认：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 阴影峰值 alpha | **45%**（sigma=7 写死）| **16%**（sigma=10，向下偏移 3px）|
| 上面板边缘压暗 | 129/234 = 55% | 16% |
| 圆角半径 | 8（`kRadius`），但视觉偏小 | 8，边界拟合偏差 0.37px |
| 抗锯齿过渡 | 1px，拐角有阶梯 | 1.25px，阶梯消失 |

阴影参数原本硬编码在着色器里（`sigma=7.0`、强度 `0.45`），现已提为
`Params::shadowSigma / shadowStrength / shadowOffsetY`。

同时 `kShadowPad` 16 → 32：sigma 变大后边距不足会把投影裁出一条硬边。
判据是让阴影在画布边缘衰减到不可见（pad/sigma = 3.2 -> alpha 0.00096）。

**测量方法上的教训**：我一度把阴影和"面板内部亮度"比，得出"压暗 32%"，
结论偏悲观；正确参照是**它背后的桌面**。另外 `WriteBmp32` 会把 alpha
合成到固定灰 200 上，早期据此推断"渲染目标有残留"是错的 —— 那条结论已撤回。

### 测试鲁棒性修复（两个真实的假失败）

* **历史聚合自检与时间相关**：合成样本用 `now - hour*3600 - 600`，
  当 `now` 位于整点后不足 10 分钟时会掉进上一个小时桶 ——
  18:50 通过、20:05 报 3 项失败。改为锚定整点 + 小时内固定偏移。
* **抓屏自检假设桌面静止**：判据是"排除后与隐藏基准差 ≤ 6"。
  机器上跑全屏游戏时背景每帧在变，差值可达 8~13，被误判为失败。
  改为先测**桌面自身抖动**作为基线，再判断是否显著超出。

### 浮窗几何由 popup.h 驱动

测试里曾经硬编码 `372x276` 与 `SP=16`，一改 `kShadowPad` 就误报三处失败。
现在测试从 `popup.h` 解析 `kPanelW/kPanelH/kShadowPad/kRadius`，
常量改了测试自动跟随。

### 5. 文字不清晰 —— 用错了 GDI+ 的文字提示

用户反馈"字体显示不清晰"。根因是 GDI+ 的命名误导：

```cpp
g.SetTextRenderingHint(TextRenderingHintAntiAlias);   // 错的
```

`AntiAlias` 在 GDI+ 里表示**不做网格拟合（unhinted）**，字形落在分数位置，
边缘发虚。正确选择是 `TextRenderingHintClearTypeGridFit`。

判据（真机截屏，与原生 GDI 文字对比）：

| 区域 | AntiAlias | ClearType | GDI 参照 |
|---|---|---|---|
| 设备名边缘梯度 | 5.63 | **6.84** | 5.43 |
| 大数字边缘梯度 | 8.47 | **9.15** | 4.67 |

**我一度否决了 ClearType，那是错的。** 我看的是导出位图放大 8x 的图，
上面有橙蓝次像素条纹 —— 但**那正是原生 ClearType 的样子**，1:1 下人眼会
融合成更锐的边缘。用整窗截屏按 1:1 对比后，ClearType 明显更实、更接近
系统 UI 文字。教训：**放大图不能用来判断次像素渲染**。

同时修掉两个次要因素：
* 字号改为整数（原来是 12.5 / 11.5 / 10.5，非整数 em 让网格拟合失效）
* `DrawTextBaseline` 的落点取整（`ascent` 几乎总是小数，
  例如 13 × 1.33 = 17.29，小数落点会让拟合失效）
* `PixelOffsetModeHighQuality`（半像素偏移）→ `Half`

设置窗口（`settings_window.cpp`）同一个问题，一并修了。

### 6. 测试会在屏幕上闪色块（用户强反馈）

用户在全屏游戏时反复看到"莫名其妙的颜色方块"。排查结果是**我自己的测试夹具**：

## 系统材质（DWM Mica/Acrylic）在本机不可用

反复测过，最后用 DPI 感知的 WPF 探针（避免坐标被虚拟化）得到明确结果：
**所有 `DWMWA_SYSTEMBACKDROP_TYPE` 模式（mica/acrylic/micaalt/tabbed）
连同 `none` 对照，客户区都是纯黑**，只有分层模式能画出内容。也就是本机
DWM 材质不生效（Windows 版本 28000 / 26H1，存在 GameViewer 虚拟显示适配器）。

因此材质只能自研 —— 而自研又受第 1 条限制（分层窗口无法真实时）。
这两条合起来说明：**下一步应当是 DirectComposition + D2D/DWrite 重构**，
而不是继续在分层窗口上打磨。

## GPU 材质渲染

三种材质都在 HLSL 里实现，实测 **1.2~1.5 ms/帧（约 700~850 fps）**。
设备：NVIDIA GeForce RTX 5060。

### 踩过的坑（都由测试或看图抓出）

**1. blit 的降饱和必须只用于云母**
无条件应用时亚克力也被降饱和，与云母结果几乎相同（平均绝对差仅 **0.52**）。

**2. 表面色留 0 会把画面混向黑色**
云母亮度 179 → 38，三材质亮度排序完全颠倒。必须显式给出 surface 颜色，
并按材质套用各自的默认值（`ApplyMaterialDefaults`）。

**3. 模糊的 sigma 口径**
PIL 的 `GaussianBlur(radius)` 里 **radius 就是标准差**。
最初写成 `sigma = radius*0.5` 且 9 抽头只覆盖 ±1σ，模糊远弱于 Python。

**4. 抽头间隔超过条纹周期 → 同相位采样，等于没模糊**
固定 9 抽头 + `step = 0.625σ` 时，亚克力 σ=26 的间隔是 **16.25px**，
正好等于测试条纹的 16px 周期，9 个抽头全落在同一相位。
改为 **1 纹素步长 + 抽头数随 σ 增长（覆盖 ±2.5σ）** 才正确。

**5. 降采样倍率必须随 σ 自适应**
固定 1/4 时，云母 σ=2 的盒滤波一次跨越整整一个条纹周期，
细节在模糊开始前就被抹掉。改为 σ 足够大才降采样，且保证低分辨率 σ ≥ 2。

**6. D3D11 不允许同一纹理同时作着色器输入与渲染目标**
违反时**写入被静默丢弃**（模糊看似没生效，实际是没写进去）。
切换渲染目标前必须 `PSSetShaderResources(0, 2, nullptr)` 解绑。

### 一个测试方法论教训

第 3~5 条**平均亮度完全测不出来**（模糊不改变均值），
`test_gpu_vs_python.py` 的亮度比 0.97~1.00 全部照常通过。
是**看渲染图**才发现 GPU 亚克力仍显示清晰条纹。

构造"模糊有效性"判据时连续错了三次：

| 判据 | 为什么错 |
|---|---|
| 绝对锐利度 | 云母 opacity 0.86 会把幅度整体压小，看着像被模糊 |
| 对比度归一化锐利度 | 面板内部竖直渐变占了主导 |
| 条纹幅度 / 原图幅度 | **仍然**被 opacity 缩放：云母只有 14% 背景透出，残留天然约 10% |

最终用**材质间相对比较**：三种材质共用同一张背景，只有云母几乎不模糊，
因此云母的残留幅度必须最高。与 opacity 无关。
数值也能对上：高斯 σ=2 对 16px 周期保留 73.5%，乘 0.14 透明度 ≈ 10.3%，
实测 9.4%。

## 实时抓屏

实测**单次抓取 1.4~5.5 ms**，空闲时自动降到 6 fps。

### 为什么不用 DXGI 桌面复制

看着更"原生 GPU"，但本机 `DuplicateOutput` 返回 `0x887A0005`
（DXGI_ERROR_UNSUPPORTED），与虚拟显示适配器有关。
`BitBlt` 复用 DC/位图后完全够用。

### 自身隐形（关键）

面板要显示"背后是什么"，但它自己就挡在那个位置，直接抓屏会**自我吞噬**。
用 `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`
让本窗口对**抓屏 API** 隐形（对肉眼仍可见）。

验证用**三次采样**（不依赖任何彩色背景夹具）：

| 采样 | 面板色占比 | 含义 |
|---|---|---|
| A 面板可见、未排除 | **100.0%** | 抓到自己 |
| B 面板可见、已排除 | **0.0%** | 不抓自己 |
| C 面板隐藏 | — | 真实背景（基准） |

`A vs B 差 86.9`、`B vs C 差 0.0`（排除后**精确等于**真实背景）。

### 实时跟随

Python 版最初是「弹出时抓一次屏 → 静态渲染」，背景变化时面板
**变化为 0.000** —— 看着像材质，其实是快照。所以必须验证"跟随"：

```
背景:  蓝    绿    红     蓝
R:     0.0   0.0   255.0  0.0     ✓ 精确跟随
回到起点偏差 0.0                  ✓ 可逆，非单向漂移
静止 1 秒出帧 6.0 fps             ✓ 空闲降频生效
```

### 踩过的坑

**1. `WS_EX_TOPMOST` 必须在窗口创建时给**
只在创建后用 `SetWindowPos` 抬升不够，窗口仍会被遮挡，
抓屏读到的是别人的内容。

**2. 纯色测试窗口的三种错误画法**（都是测试夹具问题）
- 普通 `WS_POPUP` + `GetDC`/`FillRect`，无 `WM_PAINT` → 被重绘成白色
- `WS_EX_LAYERED` + `ULW_ALPHA`，但 `CreateCompatibleBitmap` + `FillRect`
  的位图 **alpha 是 0** → 窗口**完全透明**
- 正确做法：处理 `WM_ERASEBKGND` / `WM_PAINT`，用画刷填色

**3. 断言"帧数够多"是错的**
空闲检测会把帧率降到 6fps（刻意的省电设计），1.3 秒本来就只有约 8 帧。
断言应改为"帧计数**持续增长**"，并把降频本身也锁进测试。

## 托盘图标与菜单

图标用 GDI+ 绘制，**先在 4 倍画布上画再缩到 16px**；
菜单用 Win32 原生 `TrackPopupMenu`。

* 主视觉是**数字本身**（粗体撑满），底部一道横条表示比例兼状态色
* 颜色：>45% 绿 / 21–45% 黄 / ≤20% 红 / 充电蓝 / 未知灰
* **历史值**（鼠标休眠）用灰 + 空心比例条，一眼看出不是实时值 ——
  比显示 "--" 有用，休眠时电量本来也不会变

### 踩过的坑

**1. `small` 是 Windows 宏**
`rpcndr.h` 里有 `#define small char`，变量名叫 `small` 会被拆成
`Bitmap char(...)`，报一串怪错误。

**2. GDI+ 的头文件顺序**
必须先 `#include <objidl.h>` 再 `<gdiplus.h>`，否则
`GdiplusImaging.h` 会因 `IStream`/`PROPID` 未定义而连锁报错。

**3. `FontFamily` 不可赋值**，且 `GetFamily()` 是**输出参数**形式。

**4. `MF_RADIOCHECK` 不存在**，应是 `MFT_RADIOCHECK` 放进类型位。

**5. tooltip 限的是字符，不是字节**（真 bug）
`NOTIFYICONDATA.szTip` 是 `WCHAR[128]` = 127 **字符**。
最初写 `out.resize(127)` —— `std::string::size()` 数**字节**，
中文一字 3 字节，只放得下约 42 个汉字，而且**可能把某个字从中间切断**
产生非法 UTF-8。改用按码点截断后为 127 字符 / 381 字节。

> 这个 bug 我**自己的测试没抓到** —— 断言写的是 `size() <= 127`（字节），
> 恰好把错误实现放过去了。修正为同时断言**字符数**、**UTF-8 合法性**、
> **是否用足配额（>100 字符）**。

### 真 bug：点击托盘毫无反应

这是用户实际报的问题（"托盘图标点击没有任何反应"）。**根因有两个，叠加在一起**：

**1. 托盘回调不是队列消息**

`Shell_NotifyIcon` 用 **`SendMessage`** 把回调直接投给窗口过程，消息**不进队列**。
而我的设计假设它是队列消息：

```
PeekMessage 循环 -> TrayIcon::ProcessMessage()   ← 真实点击根本走不到这里
窗口过程收到 kTrayCallbackMsg -> return 0        ← 被静默吞掉
```

**2. v4 模式下新旧事件码同时到达**

设了 `NOTIFYICON_VERSION_4` 后，一次真实左键单击会依次收到：

```
lp=0200 (WM_LBUTTONDOWN)  旧版
lp=0201 (WM_LBUTTONUP)    旧版
lp=0202 (WM_LBUTTONUP)    旧版
lp=0400 (NIN_SELECT)      v4    ← 真正的"单击"
```

- 只认旧码 → 无反应
- **新旧都认 → 触发两次** → 左键表现为"浮窗开了立刻关"（`TogglePopup` 跑两遍），
  右键表现为菜单弹三次

修复：**在窗口过程里处理回调**（这才是规范位置），并按
`NIM_SETVERSION` 是否成功来选择事件集 —— v4 只认 v4 码，旧版只认旧码。

### 为什么原测试没抓到（值得记住的教训）

原来的合成测试**通过了**，因为它犯了和实现**完全相同的两个错误假设**：

| 测试做法 | 真实情况 |
|---|---|
| 用 `PostMessage` 投递 | shell 用 `SendMessage`，不进队列 |
| 投递 `WM_LBUTTONUP` | v4 下真实左键是 `NIN_SELECT` |

**测试和实现共享同一个错误模型时，测试必然通过。**
这也解释了为什么"只要投递我自己代码认识的那个消息，测试就是绿的"。

定位手段是**在回调路径里加临时日志**，用真实 `SendInput` 点击后读日志：

```
WNDPROC callback: lp=10202 -> invoking onClick   ← 第 1 次
WNDPROC callback: lp=10400 -> invoking onClick   ← 第 2 次
```

一眼就看出"消息到了窗口过程"和"一个点击触发两次"。

### 现在的回归测试

- `probe_tray_events.py` —— 逐个事件码验证是否被响应
- `verify_tray_realclick.py` —— **`SendInput` 真实点击**（唯一忠实的复现方式），
  含"点空白处不应有反应"的对照组
- `--test-tray` 里新增 7 个**事件分发逻辑**用例（v4/旧版各触发一次、右键不误触左键）

### 验证托盘图标"真的在任务栏上"

这件事我**连续错了三次**：

| 尝试 | 结论 | 为什么错 |
|---|---|---|
| 1. 两个时刻像素差分 | "变化 132 列，图标存在" | 那 132 列是**时钟和网速** |
| 2. 只比图标区的受控差分 | 差值 **0.0** | 图标**根本不在任务栏**；我一直把 **Python 版的 "94"** 当成自己的 |
| 3. 查注册表 | 找到根因 | Win11 把新图标放**溢出菜单**：我们的 `IsPromoted` 为空，`pythonw.exe` 是 `1` |

**可靠证据**是 Windows 自己存的图标快照
（`HKCU\Control Panel\NotifyIconSettings\<hash>\IconSnapshot`，PNG）。
解码我们的条目，内容正是 **"--" + 空心比例条**。不依赖像素、不依赖时序。

## 详情浮窗

`372x204` 画布 = 面板 `340x172` + 四周 16px 投影/折射采样边距。
可拖动，12 秒自动关闭，材质跟随背景实时变化。

### 为什么必须用分层窗口

材质要在窗口内部逐像素合成（含圆角外的透明与投影），普通窗口做不到。
代价：**分层窗口绕过 DWM 合成，用不了系统材质** —— 所以必须自己抓屏
+ GPU 渲染。

### 踩过的坑

**1. `Image::Resize()` 会清空缓冲区**
写完合成结果后又调了一次 `Resize`（想"确保尺寸"），把画面整个抹掉。

**2. `--percent` 被注册了两次**（真 bug）
两个处理分支，**第一个永远先命中并吃掉参数**，第二个永不执行 ——
`--dump-popup --percent 15` 拿到的仍是默认 94，五个状态渲染出一模一样的图。

**3. 强调色没写 alpha 字节**（真 bug）
`Palette` 里 `text` 等写了 `0xFF...`，而 `accent*` 只写了 RGB
（最高字节 0 = **全透明**）。进度条填充与"严重电量"红字全部画不出来。
现在头文件里明确注明**所有颜色字段都是 0xAARRGGBB**。

**4. R/B 通道互换**（真 bug，最难发现）
三套通道约定在这里交汇：

| 来源 | 内存字节序 |
|---|---|
| GPU 读回 `DXGI_FORMAT_R8G8B8A8_UNORM` | R,G,B,A |
| GDI+ `PixelFormat32bppARGB` | B,G,R,A |
| `CreateDIBSection` 32bpp BI_RGB | B,G,R,A |

（GDI+ 的 "ARGB" 是 `0xAARRGGBB` 打包值，小端展开就是 BGRA。）
后果：**15% 显示成蓝色**（红 200,44,38 → 38,44,200），
**充电条显示成橙色**（蓝 0,120,212 → 212,120,0）。

> **数值对比完全测不出来**：换通道几乎不改变亮度与均值，
> 粗粒度平均差始终在 16~18。只有**看图**才发现。

**5. 修复通道时自己引入的回归**
第一版修法是"复制一份 BGRA 给 GDI+ 画"，但返回的仍是原始 canvas
—— **整个浮窗没有文字**，而编译与数值检查全部正常。

**6. 测试的取样点选错**
集成验证采样面板正中一小块，那里恰好是数字与进度条之间的空白，
标准差 0.98 被判为"没渲染内容"。浮窗其实完全正常。

## 设置窗口

`456x458`，全部自绘控件（滑块 / 开关 / 单选行 / 材质卡 / 按钮），
背景同样是 GPU 材质。不用 Win32 原生控件：主题不一致、高 DPI 布局难控。

### 最关键的验证：点击是否真的生效

Python 版的设置窗口**整个不可操作**，症状是"鼠标一直转圈圈"。
根因是 `GWLP_USERDATA` 用 `-8` 写入 —— 那个值是 `GWLP_HWNDPARENT`，
真正的 `GWLP_USERDATA` 是 **-21**。对象指针写错槽位后，窗口过程拿到的
永远是 `nullptr`，所有鼠标消息落到 `DefWindowProc`。

**"窗口存在"这种检查当时会通过，而窗口其实毫无用处。**
所以验证必须**点下去并确认状态变了**：

| 操作 | 结果 |
|---|---|
| 点击「120 秒」+「保存」 | 配置 interval `30` → **`120`** ✓ |
| 拖动低电量滑块到 90% + 保存 | `low_threshold` `20` → **`81`** ✓ |

点击通过 `PostMessage(WM_LBUTTONDOWN/MOUSEMOVE/LBUTTONUP)` 走**真实消息
管线**注入，不是直接调内部函数 —— 否则测不到 `GWLP_USERDATA` 这类接线错误。

### 踩过的坑

**1. 自检的布局重叠检查本身是错的**（误报）
手工维护的"控件 y 范围"表报"分组3 与 材质卡 重叠"。
实际标签是**按基线**绘制在 `y+10`，文字占据基线**之上**，根本没压到卡片。
改为**测量渲染结果**：逐行统计墨迹，找出连续内容行带，确认互不交叉。

**2. 窗口过程是自由函数，碰不到私有成员**
把鼠标处理提成 `OnMouseDown/OnMouseMove/OnMouseUp` 三个成员函数 ——
顺便让交互逻辑**可以脱离消息循环单测**。
